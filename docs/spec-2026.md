# Packet format 2026 (F1 25 "2026 Season Pack")

Distilled wire spec for `packetFormat == 2026`, as implemented by
`src/f126/parser/spec_2026.py`. Read [`spec-2025.md`](./spec-2025.md) first —
this format is expressed as a diff against it, and `spec_2026.py` literally
imports and mutates the 2025 field tables so the two cannot drift apart.

## Sources

1. **[volodymyr-fed/F1Game.UDP](https://github.com/volodymyr-fed/F1Game.UDP) v26**
   (commit `df33608`, *"feat: add support for 2026 Season Pack telemetry
   data"*). C# structs with `[StructLayout(LayoutKind.Sequential, Pack = 1)]`
   and explicit `static int ISizeable.Size` constants per packet.
2. **A live PS5 capture of the user's own session** — Bahrain P1, F1 25
   v1.24, 10,223 packets at 10 Hz plus 25,006 packets at 60 Hz. This is the
   authority wherever anything disagrees.

The EA forum page that hosts the official spec
(`forums.ea.com/blog/f1-games-game-info-hub-en/…/12187347`) returns **HTTP 403**
from this environment, so it could not be consulted directly. Everything below
is corroborated by at least two of: the C# library, the live capture, and
physical plausibility.

Header sample from the capture: `packetFormat=2026`, `gameYear=25`,
`gameMajorVersion=1`, `gameMinorVersion=24`, `packetVersion=1`,
`playerCarIndex=21`. Note **`gameYear` stays 25** — the 2026 pack is DLC on
F1 25, not a new title.

## What changed from 2025

Nine layout changes plus one payload change. Everything else is byte-identical.

| # | Change | Effect |
| --- | --- | --- |
| 1 | **Car array length 22 → 24** (`ProtocolLimits.MaxCars`) | moves every array-shaped packet |
| 2 | `CarMotionData`: g-forces float32 → **packed int16** | 60 → 54 B/car |
| 3 | `CarTelemetryData`: `engineTemperature` uint16 → **uint8** | 60 → 59 B/car |
| 4 | `CarStatusData`: **+ `ersHarvestLimitPerLap`** (float) | 55 → 59 B/car |
| 5 | `ParticipantData`: `driverId`, `networkId`, `teamId` uint8 → **uint16** | 57 → 60 B/car |
| 6 | `LobbyInfoData`: `teamId` uint8 → **uint16** | 42 → 43 B/car |
| 7 | `TimeTrialDataSet`: `teamId` uint8 → **uint16** | 24 → 25 B |
| 8 | `PacketSessionData`: **+173 B tail** (active-aero zones, DRS zones, start reaction time, extra assists) | 724 → 897 B body |
| 9 | **New packet id 16, `CarTelemetry2`** | 10 B/car |
| — | `COLL` event payload gains a `severity` byte | 2 → 3 B |

The header itself is unchanged at 29 B, which is what makes per-packet dispatch
on the leading uint16 possible.

## New and changed records

### `CarMotionData` — 54 B (id 0)

Identical to 2025 except the three g-force components are `int16` rather than
`float32`:

| Offset | Type | Field |
| --- | --- | --- |
| 0 | 3 × float | world position X, Y, Z |
| 12 | 3 × float | world velocity X, Y, Z |
| 24 | 6 × int16 | forward dir X/Y/Z, right dir X/Y/Z (÷ 32767) |
| 36 | **3 × int16** | **g-force lateral, longitudinal, vertical** |
| 42 | 3 × float | yaw, pitch, roll |

#### The g-force scale: 1024 counts per g

Neither reference documents the conversion — F1Game.UDP exposes the raw `short`
and the EA spec page is unreachable. It was determined **empirically from the
capture**:

- Longitudinal acceleration was computed independently from the packet's own
  **float32 world-velocity vector** (`Δv/Δt`, unquantised) projected onto the
  car's forward axis, then compared against the packed value.
- At **1024 counts/g** the median residual is **0.022 m/s²** over 835 samples.
  The nearest alternatives are far worse: 512 → 1.54 m/s², 2048 → 0.82 m/s²,
  4096 → 1.46 m/s², 256 → 4.15 m/s².
- The resulting peaks are physically right for an F1 car: **4.53 g** braking
  and **4.00 g** lateral. A divisor of 4096 would imply a 1.0 g peak lateral
  load, which is not credible; 32767 (the divisor the packet's own note gives
  for its *direction* vectors) would imply 0.13 g.

So the encoding is fixed-point with a 1/1024 g quantum, representable range
±32 g. The constant lives in one place, `spec_2026.G_FORCE_DIVISOR_2026`, and
is regression-tested against the committed capture fixture.

As a side benefit this cross-check validates the whole 2026 offset derivation:
`|world_velocity| × 3.6` agrees with the separately-decoded `CarTelemetry`
speed field to a **median of 0.022 km/h**.

**Sign convention:** EA's lateral g is inverted relative to the car's right
direction vector (verified: median residual 0.012 m/s² negated vs 0.048
as-is). This convention is identical in 2025, where the field is a plain
float, so the parser passes the value through **unchanged in both formats**
rather than re-defining EA's convention.

### `CarTelemetryData` — 59 B (id 6)

Only `engineTemperature` changed, uint16 → uint8, which shifts every field
after it by one byte. Live capture shows engine temp in 110–114 °C, comfortably
inside a uint8.

### `CarStatusData` — 59 B (id 7)

`ersHarvestLimitPerLap` (float) is inserted **after** `ersHarvestedThisLapMGUH`
and **before** `ersDeployedThisLap`.

### `ParticipantData` — 60 B (id 4)

`driverId`, `networkId` and `teamId` all widen to uint16. The team enum now
reaches 486 (`Cadillac26`), which no longer fits in a byte — this is why the
widening happened. Audi (485) and Cadillac (486) join the grid; the 2026
constructor ids occupy 476–486.

### `PacketSessionData` — 897 B body (id 1)

Everything up to and including `sector3LapDistanceStart` (body offset 720–724)
is byte-identical to 2025, which is why `SessionView` needs no format-specific
handling. The new 173 B tail is:

| Type | Field |
| --- | --- |
| uint8 | `activeAeroTrackStatus` (0 = full, 1 = partial) |
| uint8 | `numActiveAeroZonesFull` |
| 8 × {float, float} | full active-aero zones (start, end lap fractions) |
| uint8 | `numActiveAeroZonesPartial` |
| 8 × {float, float} | partial active-aero zones |
| uint8 | `numDrsZones` |
| 4 × {float, float} | DRS zones |
| float | `startReactionTime` |
| uint8 | `antiLockBrakesAssist` |
| uint8 | `tractionControlAssist` |
| uint8 | `dynamicRacingLineHiVis` |
| uint8 | `dynamicRacingLineColourBlind` |
| uint8 | `recurringRewindPrompt` |

### `CarTelemetry2Data` — 10 B (id 16, new)

| Offset | Type | Field |
| --- | --- | --- |
| 0 | uint8 | `activeAeroMode` (0 = corner mode, 1 = straight mode) |
| 1 | uint8 | `activeAeroAvailable` |
| 2 | uint16 | `activeAeroActivationDistance` |
| 4 | uint8 | `overtakeAvailable` |
| 5 | uint8 | `overtakeActive` |
| 6 | uint16 | `overtakeActivationDistance` |
| 8 | uint8 | `regulations2026Applicable` |
| 9 | uint8 | `isDrivingWrongWay` |

## How the 2026 views are assembled

`types.py` puts two things on `TelemetryView` that do **not** arrive in the
CarTelemetry packet, so `PacketParser` keeps a small per-session merge cache:

| `TelemetryView` field | Arrives on | Behaviour |
| --- | --- | --- |
| `aero_mode` | CarTelemetry2 (id 16) | cached, read by id 6 |
| `energy_store_j` | CarStatus (id 7) `ersStoreEnergy` | cached, read by id 6 |
| `energy_deploy_mode` | CarStatus (id 7) `ersDeployMode` | cached, read by id 6 |

Consequences, all deliberate and tested:

- **id 16 emits no view of its own** (`ParsedPacket.view is None`). It is still
  counted as parsed. Emitting a second `TelemetryView` per frame would double
  the telemetry rate with duplicate core data.
- `aero_mode` and the energy pair are `None` until the corresponding packet has
  been seen once in the current session, and **reset when `sessionUID`
  changes**.
- Because id 16 arrives alongside id 6 at the same cadence, `aero_mode` can lag
  by at most one frame (≤ 17 ms at 60 Hz).
- `StatusView.ers_*` are all `None` on 2026, per the `types.py` contract
  ("energy system lives in `TelemetryView`"), even though the fields are still
  physically present on the wire.
- `TelemetryView.drs_open` is `None` on 2026: the DRS byte still exists in the
  wire struct but is meaningless under 2026 regulations, which use active aero.
  `StatusView.drs_allowed` *is* still decoded, since it is a permission flag
  that remains well-defined.

## Measured packet cadence

Live-measured on the user's PS5, 60 Hz capture (25,006 packets over 60.00 s).
Only six ids follow the in-game send-rate setting; the rest have fixed
independent cadences.

| id | Packet | @60 Hz setting | @10 Hz setting | Follows send rate? |
| --- | --- | --- | --- | --- |
| 0 | Motion | 59.90 Hz | 9.73 Hz | ✅ |
| 2 | LapData | 59.90 Hz | 9.73 Hz | ✅ |
| 6 | CarTelemetry | 59.91 Hz | 9.73 Hz | ✅ |
| 7 | CarStatus | 59.91 Hz | 9.73 Hz | ✅ |
| 13 | MotionEx | 59.90 Hz | 9.73 Hz | ✅ |
| 16 | CarTelemetry2 | 59.90 Hz | 9.73 Hz | ✅ |
| 11 | SessionHistory | 19.97 Hz | 19.45 Hz | ❌ fixed 20 Hz |
| 12 | TyreSets | 19.97 Hz | 19.45 Hz | ❌ fixed 20 Hz |
| 10 | CarDamage | 9.97 Hz | 9.74 Hz | ❌ fixed 10 Hz |
| 1 | Session | 1.98 Hz | 1.94 Hz | ❌ fixed 2 Hz |
| 5 | CarSetups | 1.98 Hz | 1.96 Hz | ❌ fixed 2 Hz |
| 15 | LapPositions | 1.00 Hz | 0.98 Hz | ❌ fixed 1 Hz |
| 4 | Participants | 0.20 Hz | 0.20 Hz | ❌ fixed 0.2 Hz |

At the 60 Hz setting this is **~417 packets/s, ~414 KB/s**. Skipping ids 5, 9,
12, 13 and 15 removes roughly a quarter of that byte volume before it reaches
any decoder.

Record format: repeating `struct.pack('<QH', monotonic_ns, payload_len)`
followed by `payload_len` raw datagram bytes.

The trimmed fixture is a contiguous ~1 MB window of the 10 Hz capture centred
on the session's hardest braking event (−4.53 g), chosen so it contains all 14
ids the live session emits *and* enough dynamics to regression-test the g-force
scale. Tests against the two full captures skip cleanly when the files are
absent.

## Discrepancies and open items

- **EA spec page unreachable (HTTP 403).** Every layout claim here rests on the
  C# library plus the live capture, which agree on all 14 observed sizes.
- **The two references disagree about nothing structural**, because they
  describe *different formats*: the C headers are 2025-only and the C# library
  is 2026-only. Where a struct exists in both and differs (Motion, CarTelemetry,
  CarStatus, Participants, LobbyInfo, TimeTrial), the difference is a real
  Season Pack change and is listed in the table above, not a documentation
  conflict.
- **`FiaFlag`** in F1Game.UDP omits `RED = 4`; the 2025 C header documents it
  and `types.py` names it. The parser keeps `RED = 4` and passes unknown values
  through, so nothing is lost either way.
- **`formula` = 13** appears in the live capture. The 2025 header documents
  0–9 only, so 13 is presumably the 2026 ruleset. The field is not surfaced in
  any view, so this is recorded for future reference only.
- **G-force scale** is empirically derived, not documented — see above. It is
  isolated in a single named constant should the official figure ever differ.
